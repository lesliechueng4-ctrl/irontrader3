# IronTrader3 观测台（Dashboard）优化建议报告

> 基于对项目全量代码（约 2.2 万行 Python 后端 + 8.1k 行前端）的重新扫描与分析，2026-09-28。
> 所有问题均标注代码出处，建议按 P0→P3 优先级排序。

---

## 一、整体架构现状（摘要）

**后端**：Flask 单体应用，`app.py` 注册 6 个 Blueprint（market / scanner / lowbuy / hero / backtest / intraday）。数据流为：

```
外部数据源(Sina/腾讯/东财/AKShare)
  → DataSourceClient（限流/重试/熔断）
  → DataFetcher（字段归一化、多源降级、全局唯一单例）
  → CacheManager（内存 LRU 500 条 + 签名 pickle 文件两级缓存）
  → 引擎层（情绪闸 / 低吸五维 / 龙头梯队 / 洗盘扫描 / 盘中信号）
  → workbench_service（纯函数聚合）
  → 路由层（另有响应级缓存 180s）→ JSON → 前端轮询
```

**前端**：`index.html` + 8 个原生 JS 模块，无图表库（Canvas 自绘）。5 个 Tab：作战大屏（默认聚合页）、日内高抛低吸（伪 Tab，实际滚动到大屏内嵌区块）、选股雷达、单票研报、回测实验室。

**用户画像推断**：A 股短线打板/低吸交易者。核心使用节奏：① 盘前/盘中第一眼判断"今天能不能做、仓位多少"（情绪闸+作战台）；② 看情绪阶段、晋级率、炸板率、连板高度；③ 看主线题材与龙头梯队买点/卖点信号；④ 盘中对持仓做分时高抛低吸；⑤ 盘后扫描、回测复盘。

**总体评价**：产品的信息架构意识是好的——作战台把"情绪闸→仓位→候选"收束成行动摘要、梯队信号徽章化、交互表格和任务恢复机制都较成熟。主要短板：**一个首屏初始化 bug 废掉了整个信息架构的入口；首屏空间分配与用户真实优先级错位；色彩语义三套并存；若干高频交互链路断裂**。

## 二、P0 —— 立即修复（功能性缺陷，直接废掉核心体验）

### P0-1 首屏核心区块不加载

**现象**：首次打开页面，情绪周期仪表盘、今日作战台、龙头梯队、板块资金流向四大核心区块永远停留在"加载中…/正在生成今日作战计划…"，直到用户手动点一次任意 Tab。

**代码证据**：
- `initLowBuy()` 只在 `switchTab()` 内被调用（`templates/index.html:541-542`），而页面加载时没有任何代码调用 `switchTab`。
- `lowbuy.js:1255` 的 `DOMContentLoaded` 只初始化自动补全和扫描设置，不调用 `initLowBuy()`。

**改进**：在 `index.html` 的 `DOMContentLoaded`（L508）中直接调用 `initLowBuy()`（或初始化时显式调用一次 `switchTab('dashboard')`）。

**理由**：这是整个信息架构的入口 bug。"今日能不能开仓、仓位上限多少"是短线用户的第一诉求，修复成本一行代码，收益最大。

### P0-2 切换到作战大屏会无声停止日内监控

**代码证据**：`index.html:554-557` 对任何非 `intraday` 的 tabName 都调用 `intradayOnTabInactive()` 停止轮询；而恢复分支 `intradayOnTabActive()` 只在 `tabName==='intraday'` 时执行——由于日内区实际嵌在 dashboard 面板内，用户从其他 Tab 切回作战大屏时监控已停止且不再恢复，状态条显示"⏸ 已暂停"，用户通常不会察觉。

**改进**：将启停逻辑改为"dashboard 面板可见且日内区在视口内即轮询"，或在 `tabName==='dashboard'` 时也调用 `intradayOnTabActive()`；同时把暂停状态做成醒目的横幅而非一行小字。

### P0-3 键盘导航到"日内高抛低吸"显示空白页

**代码证据**：日内 Tab 按钮 `data-tab="intraday"`（`index.html:93`）但没有 `id="tab-intraday"` 的面板；点击路径走 `jumpToIntraday()` 绕过，键盘路径（左右方向键，`index.html:560-574`）会调用 `switchTab('intraday')`，导致所有面板被取消激活、页面空白。

**改进**：在 `switchTab` 中对 `intraday` 特判走 `jumpToIntraday()` 逻辑，与点击路径统一。

## 三、P1 —— 高频使用的关键链路（每天多次碰到）

### P1-1 首屏布局重排：核心信号上提，日内区按需展开

**现状**：作战大屏垂直堆叠 7 个大区（`index.html:109-310`），其中日内观测台（4 张 Canvas 图 + 5 张信号卡）独占约一屏半，且默认标的硬编码为贵州茅台（`index.html:157` value="600519"，`intraday.js:1026-1032` 打开页面 500ms 后自动启动监控，触发 3 个 API + 2 个定时器）。结果是打板最核心的**晋级率、空间高度、梯队买点、涨停池被压到第 3~4 屏**。

**建议的目标信息层级（与用户使用节奏对齐）**：

| 屏序 | 内容 | 理由 |
|---|---|---|
| 第一屏 | 情绪闸+仓位上限（一句话行动摘要）、情绪周期+6 项指标（晋级率/炸板率/连板高度加大字号）、今日作战台 3 只优先候选 | 回答"能不能做、做多少、做什么" |
| 第二屏 | 题材龙头梯队（晋级率/空间高度表头已设计好，只需上提）+ 涨停 Top20 + 主线热度 | 回答"主线是谁、龙头几板、有没有买点" |
| 第三屏（折叠/按需） | 日内分时观测台：默认不启动监控，改为从作战台候选/梯队/自选股点选后才启动；默认标的不应是茅台，应为"最近查看/自选第一只" | 日内是对单票的执行工具，不应占据全局首屏 |

**理由**：日内区嵌在 dashboard 里本是"少切换"的好设计，但它服务的对象是"已选定的单票"，而非全局概览。把它默认展开且默认茅台，等于让所有用户每天先看到一只大概率与自己无关的股票。

### P1-2 统一色彩语义为 A 股红涨绿跌

**代码证据**（三套语义并存）：
1. `app.js:94`：市场五态涨跌幅 `changePct >= 0` 用 `var(--accent-success)` 即**绿色** —— 违反红涨绿跌；
2. `styles.css:1297-1298, 1428-1429`：`.positive`（资金流入）= 绿色、`.negative` = 红色，与梯队/情绪/日内模块（`intraday.js:213-218` 涨红跌绿）相反，板块资金流入 TOP10 显示为绿色（`lowbuy.js:731,739`）；
3. 信号语义又是第三种：低吸买点 ▲ 用绿、高抛 ▼ 用红（`intraday.js:489`）。

**改进**：定义两个语义变量组并全站统一——`--up/--down`（涨跌：红/绿）与 `--buy/--sell`（操作：可自定义但与涨跌解耦）；逐处替换 `app.js:94`、`styles.css` 的 `.positive/.negative`、资金流横条。同一个"绿色"在不同卡片含义相反，对需要秒级扫读的短线用户是持续的认知税。

### P1-3 修复按名称搜索链路

**代码证据**：研报搜索框占位符承诺"输入股票代码或名称…贵州茅台"（`index.html:365`），但 `app.js:52-54` 用 `replace(/[^0-9]/g,'')` 删掉所有非数字字符；而接 `/api/search` 的自动补全绑定在 `type="hidden"` 的 `#lowbuy-code-input` 上（`index.html:372`，`lowbuy.js:1051-1052`），用户永远看不到补全下拉。按名称搜索整条链路是断的。

**改进**：把 `setupCodeAutocomplete()` 绑到可见的 `#stockInput`（和日内区 `#intradayCodeInput`），输入名称时下拉选择后回填代码。

### P1-4 刷新不再闪烁：替换"清空再填"的渲染方式

**代码证据**：每 30s 轮询时 `loadSectors` 先 `innerHTML='加载板块数据...'` 清空再重建（`lowbuy.js:703`），`loadDragonLadder` 同理（`ladder.js:23-25`）——页面上每 30 秒一次内容闪烁。

**改进**：改为"保留旧内容 + 角落刷新指示器"，拿到新数据后整体替换；或做轻量 diff（按 key 更新行）。配合骨架屏（首次加载时）替代全站的"加载中…"文字。

## 四、P2 —— 数据一致性与轮询策略（影响"敢不敢相信屏幕上的数字"）

### P2-1 统一各面板的数据新鲜度

**代码证据**：前端每 30s 同时刷的接口分属不同缓存层——`/api/market-state`（实时算）、`/api/hotzt`（底层 30s TTL）、`/api/zt-pool`（响应缓存 180s）、`/api/today-workbench`（180s）、`/api/dragon-ladder`（25s）。同一时刻"涨停数量"和"涨停池表格"可能差一代数据；zt-pool 刷新时是**同步重算整个涨停池逐股决策**（`market_routes.py:573-616`），用户点🔄后可能转圈数十秒。

**改进**：
1. 后端给每个聚合响应统一携带 `as_of`（数据时间戳）+ `stale` 标志（目前只有 hotzt 有，`data_fetcher.py:556-559`），前端在每个卡片右上角统一渲染"数据时间 / 已过期"水印——**先让用户能看懂新旧，再谈消灭新旧**；
2. refresh 改为异步：立即返回 `building` 状态 + 后台重建，前端轮询完成，避免请求线程长时间阻塞；
3. 中长期可考虑 SSE 替代多路轮询（当前无 WebSocket/SSE，30s×8 接口 + 日内 5s/10s×3 接口）。

### P2-2 轮询感知页面状态与交易时段

**代码证据**：`app.js:38-42` 的 30s 轮询不区分当前 Tab、不监听 `visibilitychange`（后台标签页照刷）；`intraday.js:50-59` 定义了 `isTradingTime()` 但**全文件无调用**（死代码），盘后/周末照样 5s/10s 轮询盘口和分时。

**改进**：接入 `document.visibilitychange`（隐藏时暂停、恢复时立即刷一次）；启用 `isTradingTime()`，非交易时段把日内轮询降为分钟级或停止；按当前 Tab 只刷可见面板。

### P2-3 消除关键指标的重复与埋没

**代码证据**：
- 重复：`app.js:126-149` 市场五态"操作建议"框把指数/MA5/偏离度原样重复渲染一遍，页面上出现两个"操作建议"标题；总仓/单仓上限在 mission 卡、情绪卡、研报结论三处重复；研报页统一结论卡与 `#analysis-panel` 结论卡内容重叠渲染两遍。
- 埋没：晋级率/空间高度（`ladder.js:111-116`）在第 4 屏；炸板率/连板高度在情绪卡 6 格小指标里（`mood.js:217-223`）字号小。

**改进**：每个指标只保留一个权威展示位；把"晋级率 / 炸板率 / 连板高度 / 涨停数"做成第一屏的 4 个大数字 KPI 条（数据源现成：ladder 头部 + 情绪 6 格），与 P1-1 的布局重排一并实施。

## 五、P2 —— 后端配套（直接影响 Dashboard 流畅度）

按对 Dashboard 体验的影响排序：

1. **`DataSourceClient._throttle` 持锁 sleep**（`data_source_client.py:240-249`）：某数据源限流等待时，所有线程连"读熔断状态"都被阻塞，表现为盘中多面板同时卡顿。改为先算等待时长、释放锁后再 sleep。
2. **`_AKSHARE_HISTORY_LOCK` 全局串行**（`data_fetcher.py:24,1055`）：全 A 扫描期间所有历史 K 线请求排队，Dashboard 单票分析（K 线/研报）同步变慢。可改为按 code 分桶锁或限制并发数而非全局串行。
3. **CacheManager 无锁**（`cache_manager.py:188-296`）：扫描高峰期 12-32 线程并发读写 OrderedDict，存在 `RuntimeError: mutated during iteration` 风险；且每 set 落盘 pickle 放大磁盘 IO。加读写锁 + 扫描模式批量落盘。
4. **任务状态三套并存**（tasks.db / `_SCAN_JOBS` / `_BT_STATE`）：进程重启后 `/api/scanners/jobs/current` 会捞出僵尸 running 任务，前端恢复出永不更新的进度条，且新旧任务并存显示两个"运行中"。给任务表加进程心跳/PID 校验，启动时把残留 running 标记为 interrupted。
5. **`/api/zt-pool` 数据故障与"真空池"不可区分**（`market_routes.py:558-559`）：数据源全挂时返回 error，前端会显示成"今日无涨停"。透出 stale/error 语义，让前端显示"数据故障"而非误导性空态。
